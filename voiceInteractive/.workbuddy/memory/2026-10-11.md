## 标注流黑屏根因定位（H.264 profile）

用户实机测试反馈"人物没有骨骼/框/属性"→ 进一步"画面是黑的"。排查过程与结论：

- SRS/worker 侧全部正常：日志有 `[SRS] 巡检画面已切到飞桨标注流 usb1_labeled`、
  `[worker] usb1 MOT 检出 1 人`、ffmpeg `frame=45 fps=7.3`、口罩与禁区事件都在报。
- **根因**：libx264 默认输出 **High profile**，而 SRS `rtmp_to_rtc` 转封装不做转码，
  profile 原样透传给 Chrome WebRTC 接收端 → 不接受 High → 黑屏。
  对比证据：SRS API 里 `usb1` 是 `Baseline`（能播），`usb1_labeled` 是 `High`（黑屏）。
  早期伪代码本来写了 `-profile:v baseline`，改写 `initcmd` 时漏了。
- **修复**：`patched_initcmd` 增加 `-profile:v baseline -bf 0`，ffmpeg 复核产物为
  `Constrained Baseline, level 3.1`。
- 新增诊断脚本 `probe_labeled_frame.py`：查 SRS 流列表 + 抓 labeled/raw 帧存图 + 平均绝对差对比，
  一次切分"worker 没推流 / 管线没检出人 / 前端播放问题"。拉流带 20s 超时（不存在的流会挂住
  VideoCapture，需 `OPENCV_FFMPEG_CAPTURE_OPTIONS=rw_timeout`）。
- worker 新增低频诊断日志：`MOT 检出 N 人` / `MOT 近 60s 未检出人员`（60s 一次），
  外加启动时打印 `拉流 X -> 推流 Y`。
## 退出时 8771 抛 KeyboardInterrupt（已修）

现象：退出时 `paddle_server.py main() -> runner.stop() -> proc.wait(timeout=25)` 抛 KeyboardInterrupt 栈。
根因：**Windows 控制台 Ctrl+C 发给共享该控制台的所有进程**（不是只给前台进程），主进程/8770/8771 都收；
8771 的 serve_forever 捕获第一次后，finally 里 stop() 等待期间再命中就抛栈 → worker+ffmpeg 漏回收。
修复：`paddle_runner.stop()` 用 `_reap()` 容忍 KeyboardInterrupt 视为超时继续 terminate→kill；
并发 stop 改等 `_stopped` Event（此前第二个调用会提前 return 导致孤儿）；
`paddle_server.main()` 清理前 SIG_IGN 且等 /shutdown 线程完成（40s）；
`main.py` 回收子进程时显式兜 `KeyboardInterrupt`（**它不是 Exception 子类，except Exception 抓不到**）。
**刻意不隔离信号**（不用 CREATE_NEW_PROCESS_GROUP）：Ctrl+C 直达子进程本身是主进程被强杀时的兜底。
回归探针 `probe_shutdown.py`（三条路径：等待被打断/并发 stop/已退出进程）。

- **踩坑记录**：`netstat`/`tasklist` 只能看端口与进程名，拿命令行要用
  `Get-CimInstance Win32_Process`（wmic 被安全策略禁用；PowerShell 工具直接输出会丢，需
  `Out-File` 落地再读）。HTTP-FLV 的 `CAP_PROP_FPS` 会返回 1000、`FRAME_COUNT` 是垃圾值，
  不可用于声明 ffmpeg `-r`。修复需重启主进程（worker 是子进程）。

## 全链路代码审查与修复（2026-10-11 晚）

对巡检链路做了一次完整审查，修复 8 处问题（含 3 个会影响功能的）：

**服务端（paddle_service/）**
1. **SSE 首帧不补 modules**（P0）：worker 只在启动那刻发一次带 modules 的 status。页面刷新/重复开始巡检时 runner 已在运行，前端就绪判定（`Array.isArray(ev.modules)`）永远等不到 → 白等 90s 后放弃标注流。修：`_handle_sse` 用 `runner.ready_modules` 补发。
2. **停止后立即重启串流**（P0）：旧 worker 回收最长 25s，期间新 worker 起来会两路同拉/同推一路流。修：`_stopping_runners` 表 + `_start_runner` 先等回收。
3. **`Popen.wait(timeout)` 在 Ctrl+C 下计时失效**（P0）：Windows 的 WaitForSingleObject 不可中断，中断延迟到返回后才抛出，实测 3s 的 wait 被拖到 60s+。修：`_reap()` 改为轮询 `poll()` + 自持 deadline。
4. **入侵高亮字典只写不删**：`_intrusion_draw[(region,track_id)]` 随 track id 累积，render_frame 每帧遍历 → 长期运行内存增长+性能退化。修：达 16 项时清过期项。
5. **`stop()` 并发 race**：`if self._stopping` 与置位非原子。修：`_lifecycle` 锁。
6. **模块变更不重建 worker**：改为比较 `requested_modules`（不能用 `modules`，它会被 worker 上报的实际模块覆盖，否则反复重建）。
7. **口罩 predictor 跨线程**：FLV 重连后捕获线程重建，GPU predictor 有线程绑定。修：`on_frame` 检测 `threading.get_ident()` 变化后惰性重建。

**前端**
8. **多路流名冲突**（P0）：`usbStreamName` 用 `camSlots.indexOf(slot)+1`，关闭中间窗口后索引重排 → 新窗口拿到正在占用的流名。修：`slot._usbIdx` 稳定自增序号。
9. `slot._paddleReady` 被置 null 后 `Promise.race([null,...])` 立即 resolve → `readyEv.modules` 抛 TypeError。修：取局部引用 + 判空。
10. `_stopOne` 未清 `alertAutoHide`/`_alertClsTimer`、未置 `lastUrl=null`（双重 revoke）。
11. 口罩告警"画面人数"语义错误（后端给的是人脸数）→ 改为"检出人脸"。
